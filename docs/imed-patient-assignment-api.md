# iMed Patient Assignment API (hospital reference)

English documentation of the hospital's **iMed Patient Assignment API**
contract (source PDF: `iMedPatientAssignmentAPI.pdf`, issued 24 Jul 2026
by iMed Core, revision 1 — "API Contract"). This is the hospital-side API
our system will call to send an already-registered visit to a destination
service point (doctor room, ER, ward, …). It is the API equivalent of the
iMed UI button `patientInfo_btnSendPatient` and creates a row in iMed's
`visit_queue`.


---

## Environments

| ENV | Base URL |
|---|---|
| UAT | `https://<uat-host>/api/v1` |
| PROD | `https://<production-host>/api/v1` |

The iMed system administrator must give the third party (us) the real
URL, the **access token**, and the real **master-data codes** (service
point ids, department ids, employee ids) before connecting.

## Flow

```
Third Party ──POST /patient-assignments──▶ iMed Web Services
   1. permission + visit-lock check
   2. service-point check (BaseDelegate.checkServicePointOpen)
   3. VisitDelegate.assignVisit  (or VisitQueueDelegate.assignSbarVisit when SBAR is sent)
   4. create visit queue row ──▶ iMed Database
   ◀── JSON response
```

## POST /patient-assignments

Sends a patient who already has a visit to a destination service point.

### Request headers

```
Content-Type: application/json
Authorization: Bearer <access-token>
```

### Request body

| Parameter | Required | Type | Description | Sample |
|---|---|---|---|---|
| `request_id` | Y | string | Reference id generated by the third party; used for duplicate-request detection (idempotency key) | `THIRD-PARTY-20260724-000001` |
| `visit_id` | Y | string | iMed visit id of the patient to send. iMed derives `patient_id` and `fix_visit_type_id` from it itself | `VISIT_ID_FROM_IMED` |
| `assign_spid` | Y | string | Destination service point id (`base_service_point_id`) | `SP_DOCTOR_01` |
| `assign_eid` | Conditional | string | Destination employee/doctor id. Required only when the destination service point requires selecting a doctor (e.g. WARD or DIAG) — iMed checks this from the master service point | `EMP00001` |
| `base_department_id` | N | string | Department id of the destination service point; if omitted iMed derives it from the master service point | `DEPT_MED` |
| `queue_number` | N | string | Desired queue number; if omitted iMed generates one by its own queue rules | `A001` |
| `sbar` | N | object | SBAR handover data; send it to use the `assignSbarVisit` flow | `{}` |

The third party must **not** send `patient_id`, `fix_visit_type_id`,
`assign_location_spid`, `assign_operate_eid`, `assign_operate_eid_type`,
`modify_eid`, or any date/time — iMed derives all of these from the visit
and from the access-token identity to preserve the audit trail.

### `sbar` object (optional handover)

All fields optional strings.

| Parameter | Description | Sample (from spec, Thai) |
|---|---|---|
| `sbar.situation` | Current situation of the patient | ผู้ป่วยมีอาการเจ็บหน้าอก (patient has chest pain) |
| `sbar.background` | Relevant history / background | มีโรคความดันโลหิตสูง (has hypertension) |
| `sbar.assessment` | Assessment result | รู้สึกตัวดี vital signs คงที่ (conscious, vitals stable) |
| `sbar.assessment_problem` | Problem found on assessment | สงสัยภาวะกล้ามเนื้อหัวใจขาดเลือด (suspected myocardial ischemia) |
| `sbar.assessment_equipment` | Equipment to prepare | ECG monitor |
| `sbar.recommend` | Recommendation for the destination unit | ประเมินโดยแพทย์โดยเร็ว (doctor to assess promptly) |
| `sbar.documentation` | Supporting documents/data | แนบผล ECG (ECG result attached) |

## Response

`Content-Type: application/json`

| Parameter | Type | Description |
|---|---|---|
| `request_id` | string | Echo of the third party's request id |
| `status` | string | iMed status, e.g. `STATUS_SUCCESS` or `STATUS_BUSINESS_ERROR` |
| `result.visit_id` | string | Visit that was sent |
| `result.visit_queue_id` | string | Queue id iMed created for this assignment |
| `result.assign_spid` | string | Destination service point id |
| `result.assign_eid` | string | Destination employee/doctor id assigned |
| `result.queue_number` | string | Assigned queue number |
| `result.queue_status` | string | Created queue status, e.g. `WAITING` or `NOT_SEND` |
| `result.sbar_id` | string | Saved SBAR id; present only when the request included `sbar` |

### 200 — success

```json
{
  "request_id": "THIRD-PARTY-20260724-000001",
  "status": "STATUS_SUCCESS",
  "result": {
    "visit_id": "VISIT_ID_FROM_IMED",
    "visit_queue_id": "VISIT_QUEUE_ID_FROM_IMED",
    "assign_spid": "SP_DOCTOR_01",
    "assign_eid": "EMP00001",
    "queue_number": "A001",
    "queue_status": "WAITING"
  }
}
```

### Error responses

All errors return `"status": "STATUS_BUSINESS_ERROR"` with a `message`
code and a Thai `message_th`.

| HTTP | `message` | Meaning (`message_th`) |
|---|---|---|
| 400 | `invalid_request` | Data missing or invalid (ข้อมูลไม่ครบหรือไม่ถูกต้อง) |
| 403 | `VISIT_LOCKED_OR_FINANCIAL_DISCHARGED` | Visit is locked or financially discharged; cannot send (visit ถูกล็อกหรือจำหน่ายทางการเงินแล้ว) |
| 409 | `VISIT_QUEUE_ALREADY_EXIST` | Patient is already in the destination service point's queue (ผู้ป่วยอยู่ในคิวของจุดบริการปลายทางแล้ว) |
| 422 | `SERVICE_POINT_NOT_AVAILABLE` | Destination service point is not open/available (จุดบริการปลายทางไม่พร้อมให้บริการ) |

## Business rules (from the spec)

1. iMed verifies the `visit_id` exists, is not locked, and is not
   financially discharged before calling `VisitDelegate.assignVisit` /
   `VisitQueueDelegate.assignSbarVisit`.
2. iMed checks the destination `assign_spid` is open via
   `BaseDelegate.checkServicePointOpen` before creating the queue; closed
   or unavailable service points are never bypassed.
3. `assign_eid` is required only when the destination service point
   requires a doctor/staff assignment (determined from the master service
   point).
4. The **source** service point and the sender identity are derived from
   the access token — never accepted from the third party.
5. If `sbar` is sent, iMed uses `assignSbarVisit` (saves the SBAR and
   creates the referral queue); otherwise the normal `assignVisit` flow.
6. On `VISIT_QUEUE_ALREADY_EXIST` iMed does not create a duplicate queue;
   the third party must **retry with the same `request_id`** — the API is
   idempotent per `request_id`.

## Display in `homeQueueWalkIn.jsp` (how iMed shows the queued patient)

On success, `AssignVisitCommand` calls `CreateQueueCommand` to insert
into `visit_queue` and then clears the visit's previous queue — the same
flow as the send-patient button. The patient appears in the destination
service point's `homeQueueWalkIn.jsp` only when **all** of:

1. `visit_queue.next_location_spid` matches the service point the user is
   viewing.
2. `visit_queue.queue_status` is `WAITING` or `NOT_SEND`.
3. `visit.active` is `"1"`.
4. `visit.financial_discharge` is `NON_DISCHARGE` or
   `INCOMPLETE_DISCHARGE`.
5. If the queue page filters by department or doctor,
   `next_department_id` / `next_operate_eid` must match the filter.
6. If the destination is Billing, extra conditions may apply based on
   prescription-send status and system configuration.

Consequently, third parties must **never insert `visit_queue` rows
directly** — always go through `assignVisit` / `assignSbarVisit` so iMed
sets queue status, sequence, timestamps, audit trail, and clears prior
queues correctly.
